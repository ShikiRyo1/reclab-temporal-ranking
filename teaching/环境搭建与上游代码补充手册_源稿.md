## 3 建立两套可解释的 Python 环境

### 3.1 主实验环境

输入是项目源码与requirements-lock.txt；输出是项目里的 .venv。首次建立时在项目根目录执行以下命令。本机已经存在的环境可跳过前3行，仅执行最后两行检查，避免把正常环境无意义重装。

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-lock.txt
.\.venv\Scripts\python.exe -m pip install --no-deps -e .
.\.venv\Scripts\python.exe --version
.\.venv\Scripts\python.exe -m pip check
```

第1行调用选定的3.12解释器建立隔离环境。第2行按锁定文件安装版本，-r表示从文件读取。第3行安装本项目的可编辑链接；-e使修改src后无需重复复制代码，--no-deps让它使用刚安装的依赖，避免重新解析。最后两行分别检查解释器与依赖约束。本机实测为Python3.12.4、无损坏依赖。

Python把 .venv 设计为可重建的环境，不应把它跨机器直接复制，也不把环境目录提交Git。来源：https://docs.python.org/3.12/library/venv.html 。这段语义与本项目安装命令相对应，具体包版本仍以仓库锁定文件为准。

若出现 No module named reclab，先确认当前目录有 pyproject.toml，再检查是否执行过第3行。若只有系统python能导入而.venv不能，说明包装错环境；始终用同一条.venv/python路径调用pip、训练和测试可以避免这一类错误。

## 6 用实际实现理解算法开销

### 6.1 先定义规模再讨论快慢

以下分析来自本项目src/reclab/models.py与rerank.py，不是对所有推荐系统的统一结论。设U为训练正反馈用户数，I为训练目录物品数，d为因子维数，N为正反馈条数，E为训练轮数，h_u为用户u的正反馈物品数，P为候选池大小，K为最终返回数。它们是计数，没有秒或字节单位。Big O描述规模增长趋势，运行时间还取决于常数、数据分布与硬件。

本次U=4,865、I=3,444、d=64、P=100、K=10。float32每个数4字节；仅用户和物品因子需要约4×(4,865+3,444)×64=2,127,104字节，约2.03MiB。这个计算不含字典、历史、元数据和Python对象，不能当成整个model.joblib或服务进程内存。

### 6.2 训练阶段哪些结构会膨胀

| 实现步骤 | 主要开销 | 本项目的限制 |
|---|---|---|
| 计数流行度 | 遍历正反馈约O(N)，计数向量O(I)空间 | 便宜，但不能表达用户差异 |
| SAR共现 X转置乘X | 粗略由各用户物品对数量之和控制；最坏O(U×I²) | 稀疏输入之后仍转成稠密I×I矩阵 |
| SAR相似度和完整评分 | I²相似度空间；稀疏乘稠密约O(N×I)，输出O(U×I) | 目录变大时内存是直接瓶颈 |
| BPR每个三元组更新 | 点积和向量梯度O(d) | 负采样重试另有开销 |
| BPR一轮 | 若每个正例一次抽样，约O(N×d) | E轮约O(E×N×d)，不是秒数预测 |
| BPR离线全部用户评分 | O(U×I×d)时间，O(U×I)输出空间 | 这份完整评分矩阵只在离线评价使用 |

SAR-style先构造稀疏binary，但overlap调用toarray，因此“用了稀疏矩阵”不代表后续不占稠密内存。I=3,444时，一张float32的I×I矩阵约45.25MiB；实际同时存在overlap、denominator、similarity等数组，峰值更高。把I扩大10倍，单张矩阵约扩大100倍。空值、临时数组与库实现会影响峰值，未做内存profiling就不报一个精确总值。

BPR训练的三元组(i,j)只要求i优于j，并非给所有未评分物品贴负标签。这里Cornac只收到正反馈，所以低评分电影可能被采为j；服务的seen过滤则排除所有已评分电影。这是统计语义与计算开销两条不同问题，不能把“抽样更快”当作“负样本更真实”。

### 6.3 一次推荐请求到底做多少工作

warm请求用用户向量与全部I个物品向量点积，约O(I×d)，再加bias。过滤历史和类别需扫描或处理候选，约O(I)量级，具体常数取决于历史及类别数据。冷启动直接取流行度分数，没有用户向量点积，但仍要过滤和排序。

rank_topk实际调用np.lexsort，先按分数降序、同分按item_id升序对全部有效候选排序，再截取前P项。因此通常按O(I log I)时间和O(I)辅助空间理解；它没有使用argpartition，不能把复杂度写成只选前K的线性选择。

重排对全目录流行度调用log1p以计算novelty，O(I)；在P个候选中归一化相关性、混合得分约O(P)，非零权重再lexsort为O(P log P)。weight=0分支保留已有顺序，避免细小浮点归一化改变原次序。取K项和构建响应还有约O(K)输出开销。小P降低第二次排序成本，并没有省去全目录第一次打分。

### 6.4 一个能验证的优化问题

如果目录从3,444扩大到100万，因子维度不变，逐请求全量点积约随I线性增加，而完整排序还带log I因子。可先考虑缓存与候选召回，或在保持同分规则的前提下研究部分选择；但近似召回会丢候选，部分选择也需要正确处理边界同分。优化后的正确性必须用排序一致性、Recall损失、延迟和内存共同验证，不能只报告“用了ANN”。

练习：将I扩大10倍，因子存储约如何变化，SAR稠密相似度如何变化？答案：物品因子部分约10倍，用户部分不因此增长；I²矩阵约100倍。再问：把K从10改成5能否让当前全量打分快一半？不能；本实现仍计算全部候选。理解这个差别，才知道应优化哪一段。

这里给的是代码结构分析，未把理论次数当成实测benchmark。原500次请求p95只适用于原机器、原目录和请求分布；本轮没有声称完成百万物品压测或近似召回扩展。

### 6.5 切分和统计也有计算成本

data.py先取全部M条评分的timestamp数组并排序，通常约O(M log M)；随后依据时间边界选行约O(M)。M包括低评分，因此不能替换成前文正反馈数N。排序数组和切分副本还会占内存。train.py计算数据指纹时另按timestamp、user_id、item_id排序；那是哈希稳定化步骤，不是时间切分函数的排序键。

metrics.py的paired_comparison先求n名用户的成对差值，再交给bootstrap_interval。后者每轮生成长度n的随机整数索引，索引差值并求均值，循环B轮，只保留B个均值。因此抽样与取均值约O(B×n)时间，额外峰值空间约O(n+B)，随后分位数计算另有成本。本次B=1,000、n=922；程序没有一次保留B×n索引矩阵，不能按922,000个索引估计当前峰值。

练习：把B翻倍、n不变，抽样工作约翻倍、保存均值数量翻倍，但每轮索引长度不变；B和n都翻倍，主要抽样工作约四倍。把它改成一次构造B×n矩阵可能更方便向量化，却会增加峰值空间，是否更快需实测。复杂度分析必须读实际循环，不能套用另一个常见写法。

### SAR 原单元 20：计算四项排序指标

原单元 20 → 执行单元 21；L1–L5；单元源码 SHA-256 前 12 位 ac294a93fa7a。

test 是真值，top_k 是推荐。此原版 SAR 没有先删掉低评分：默认 binary 相关性把测试表中出现的物品视为相关。传 col_rating 不会自动执行 rating≥4。

```python
# Ranking metrics
eval_map = map_at_k(test, top_k, col_user="userID", col_item="itemID", col_rating="rating", k=TOP_K)
eval_ndcg = ndcg_at_k(test, top_k, col_user="userID", col_item="itemID", col_rating="rating", k=TOP_K)
eval_precision = precision_at_k(test, top_k, col_user="userID", col_item="itemID", col_rating="rating", k=TOP_K)
eval_recall = recall_at_k(test, top_k, col_user="userID", col_item="itemID", col_rating="rating", k=TOP_K)
```

L1：注释划分排序指标区块，与下一单元的评分误差区分。

L2：map_at_k 先计算每个命中位置的 Precision@r，再按 min(K, 真值物品数) 归一化并对用户取平均。此固定版本的 map_at_k 与分母用全部真值数量的 map 函数不同。

L3：ndcg_at_k 对前面位置的命中给更大权重，再除以该用户理想排序的 DCG。默认 score_type=binary、discfun_type=loge；DCG 与 IDCG 同时换为 log2 不改变比例。

L4：precision_at_k 计算命中数/K，再对可共同评估用户平均；不是“预测评分准确的百分比”。

L5：recall_at_k 计算命中数/该用户全部测试真值数量，再平均。本协议没有提前删除训练目录外的测试物品，所以不能套用独立 1M 实验的可达目标分母。


这里用 h_r 表示第 r 个推荐是否命中（0 或 1），R_u 是用户 u 在原测试表中的物品集合。Precision@r 是截至 r 的命中比例。下式是本固定版本 map_at_k 的分母：

$$AP@K=\frac{\sum_{r=1}^{K}h_r\,Precision@r}{\min(K,|R_u|)}$$

再对评估用户取平均得到 MAP。Precision@K 的分母是 K；Recall@K 的分母是该用户全部真值物品数量。NDCG 把命中折扣之和除以同一用户的理想折扣之和：

$$NDCG@K=\frac{\sum_{r=1}^{K}h_r/\log(1+r)}{\sum_{r=1}^{\min(K,|R_u|)}1/\log(1+r)}$$

教学手算：K=3，真值有 2 个物品，推荐命中序列为 [1,0,1]。Precision=2/3，Recall=1，AP=(1+2/3)/2=5/6；NDCG=(1+1/2)/(1+1/log2(3))≈0.9197。这里是自造小例子，不是用户 54 的真实结果。


### SAR 原单元 21：评分误差到底测了哪些行

原单元 21 → 执行单元 22；L1–L5；单元源码 SHA-256 前 12 位 3df70c59890f。

这些函数先按 userID、itemID 对 test 与 top_k 做内连接（inner join）。因此只评价两表交集中的评分预测，不是在全部 25,008 条测试评分上预测 RMSE。

```python

```

L1：注释表明下面测评分数值误差，而不是推荐顺序。

L2：RMSE 是误差平方均值再开根号，大误差受罚更重；本次为 1.229246。

L3：MAE 是绝对误差均值，单位仍是评分分数；本次为 1.033912。

L4：R²=1−残差平方和/真值离均差平方和；本次 −0.511334，表示在该交集上按平方误差衡量，还不如用交集真值均值预测。负值不是程序自动报错。

L5：解释方差为 1−Var(y−ŷ)/Var(y)；本次 0.098494。它用残差方差，R²用残差平方和；存在系统性偏移时两者可以明显不同。

### SAR 原单元 22：二值化与 logloss 的边界

原单元 22 → 执行单元 23；L1–L10；单元源码 SHA-256 前 12 位 1fc51e02ee33。

L1–L3：L1 设阈值 2；L2 复制 test 避免改掉后续原评分；L3 使用严格 rating>2 得到 0/1，所以评分 2 仍是 0。这不是 BPR 的阈值 3.5。

L5–L6：L5 复制预测表；L6 先转浮点，再对所有用户的 prediction 整列做 min–max 缩放。缩到 [0,1] 只是数值变换，不能据此断言预测已校准为概率。

L8–L10：L8 调用 logloss，L9 传入二值真值与缩放预测并声明键列，L10 结束。底层仍先按键内连接，再计算二元交叉熵；本次 0.569153。不要把它解释成全面评价未曝光项目的概率模型。

空行 L4/L7 仅分隔逻辑，不执行操作。


用 y 表示交集中的真实评分，ŷ 表示对应 prediction，n 为交集行数，则 RMSE 是平方误差平均后开根号，MAE 是绝对误差的平均。不要因 normalize=True 就把 SAR 视为专业评分回归器：原项目也说明它主要面向排序。

$$RMSE=\sqrt{\frac{1}{n}\sum_{i=1}^{n}(y_i-\hat y_i)^2},\qquad MAE=\frac{1}{n}\sum_{i=1}^{n}|y_i-\hat y_i|$$

logloss 的 y 改成 0/1、p 改成缩放值后，单行损失为 −y log(p)−(1−y)log(1−p)。库对数值端点有处理，不能手工把 log(0) 当成项目真实输出。本例只示范调用；未经校准、且只在推荐与真值交集上评价，不能据此得出整体点击概率质量。
